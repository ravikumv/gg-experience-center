iWhy GoldenGate for database migration

A database migration — moving a schema from an old engine, version, or platform to a new one — traditionally means a maintenance window: stop the application, export/copy the data, load it at the target, re-point the application, go live. For small databases that's fine. For a multi-terabyte, always-on system, that window can be hours or days the business cannot afford.

Oracle GoldenGate turns that single big-bang cutover into two parallel tracks that run while the source stays live and writable: a one-time Initial Load of existing data, and a continuous Change Data Capture (CDC) stream of everything that changes at the source from the moment the load started. The target keeps catching up in near real time until the two are in sync — at which point cutover is a short, low-risk switch rather than a long outage.

Prepare Source & Target

Enable supplemental logging / ADD TRANDATA at the source; provision and pre-create target schema (DDL conversion for heterogeneous targets); size trail files, network bandwidth, and target apply resources.

Days before migration
4

Start CDC Capture First

Start the Extract capturing changes before the Initial Load begins, so no transaction committed during the (potentially long) bulk copy is ever lost — it simply queues in the trail until Replicat is ready to apply it.

Migration day
5

Initial Load

Bulk-copy the existing data using GoldenGate Direct Load, a file-to-Replicat load, or a native utility (Data Pump / RMAN / external table) — whichever suits the data volume and source/target combination.

Migration day
6

CDC Catch-Up & Sync

Replicat applies the backlog of changes captured during the load, then continues in near real time. Monitor end-to-end latency until it stabilizes at seconds, not minutes.

Hours to days
7

Validate

Reconcile row counts and checksums/hashes between source and target (e.g. GoldenGate Veridata or custom reconciliation), confirm sequences, constraints, and dependent objects match.

Before cutover
8

Golive / Cutover & Fallback

Briefly quiesce source writes, let final lag drain to zero, switch the application connection to the target, and optionally reverse CDC direction for a rollback safety net before decommissioning the source.

Cutover window — typically minutes

iiiWhat makes this "near-zero downtime"

The outage window shrinks to just the time it takes to: stop new writes at the source, let the last few seconds of already-captured changes drain through CDC, flip the application's connection string, and resume writes at the target. Everything else — the bulk copy and the vast majority of change synchronization — happens while the business keeps running.

iHow the advisor reasons

  • Zero-downtime + any volume almost always points to Extract-first CDC with a parallel Initial Load and a short cutover window — the pattern covered in the Live Simulator.
  • Large volume favors a native bulk-load utility (Data Pump, RMAN, cloud import service, or bulk export/import) for the Initial Load instead of GoldenGate's row-by-row Direct Load, with CDC layered on top to catch up.
  • Heterogeneous engines add DDL/data-type conversion work up front and usually rule out GoldenGate's fastest same-engine load paths, pushing toward file-based bulk load plus CDC.
  • Data warehouse / lakehouse targets typically only need Replicat delivering to a staging or landing layer — transformation and modeling happen downstream, not in the migration path itself.
  • Full maintenance window acceptable can simplify to a native export/import with no CDC at all — though most teams still add CDC for a safety margin and fast rollback.

iChoose a migration pattern

Select a pattern to see its GoldenGate process topology. All three share the same backbone — Extract at the source, trail files, Replicat at the target — but differ in load method and target shape.

Oracle → Oracle (on-prem to OCI / Exadata Cloud / Autonomous Database). Same engine end-to-end, so GoldenGate Direct Load or Data Pump can move data at near-native speed, and datatypes/DDL carry over with minimal conversion.

Because both ends speak Oracle natively, teams often use RMAN duplication, Data Pump over a database link, or GoldenGate's own Direct Load for the bulk copy, then rely on GoldenGate purely for CDC catch-up and cutover.

Cross-engine (e.g. Microsoft SQL Server → PostgreSQL, or MySQL → Oracle). Datatypes, identity/sequence generation, trigger logic, and DDL are engine-specific, so a conversion step (manual or tool-assisted, e.g. Oracle Database Migration Service / SQL Developer) precedes the data movement. GoldenGate's own datatype mapping handles ordinary column conversions in-flight.

GoldenGate Extract is DDL-agnostic about the target — it captures logical row changes, and Replicat applies them against the pre-mapped target schema. The conversion layer runs once, up front; from then on CDC just keeps flowing.

Migrating operational data into an analytics platform (Snowflake, BigQuery, OCI Data Lakehouse). Here GoldenGate's job is narrower: land clean, ordered change data into a target table or staging layer. Modeling, transformation, and medallion-style layering happen downstream in the target platform, not inside the replication path.

GoldenGate delivers only to the landing/staging layer — it does not model curated or analytics-ready structures itself. That transformation is the target platform's job, run on its own schedule, decoupled from replication latency.

iiiReading a real dashboard

  • Replication lag should trend toward, and hold at, single-digit seconds before cutover is considered safe.
  • Rows migrated vs. source row count tells you how far through Initial Load (or CDC backlog) the migration is.
  • Cutover readiness in production tooling typically gates on: lag threshold met, zero unresolved validation mismatches, and no active long-running source transactions.
  • Teams commonly build this view on top of the GoldenGate Microservices REST API (Performance Metrics service) rather than screen-scraping logs.

1Sizing & supplemental logging

  • Enable minimal supplemental logging at the database level, plus ADD TRANDATA per table capturing at least the primary/unique key columns — the same prerequisite that underpins every other module in this suite.
  • Size trail files and disk for the peak change rate, not the average, and account for the backlog that accumulates while the Initial Load is running.
  • Right-size parallel Replicat threads to the target's apply capacity; over-parallelizing against a small target instance just creates lock contention.

2Network & security

  • Use encrypted trail files and TLS for Extract-to-Replicat communication, especially across a WAN or cloud interconnect (FastConnect, Direct Connect, ExpressRoute).
  • Pre-provision enough bandwidth for the Initial Load's bulk transfer window — it's usually the single largest data-movement event in the whole project.
  • Scope database and OS credentials for GoldenGate service accounts to least privilege, and rotate them after cutover.

3Initial Load method selection

  • Prefer native bulk utilities (Data Pump, RMAN, cloud import services, native COPY/bulk-insert) for large tables — they generally outperform GoldenGate's row-by-row Direct Load.
  • Reserve GoldenGate Direct Load or file-to-Replicat load for smaller tables, heterogeneous targets without a fast native path, or environments where a single consistent tool is preferred end-to-end.
  • Always start Extract capturing CDC before the bulk load begins, so nothing committed mid-load is lost.

4CDC & trail management

  • Monitor checkpoint progress and trail growth continuously during the catch-up window; a stalled Replicat quickly becomes a large backlog.
  • Set trail purge/retention policy only after confirming Replicat has durably applied and checkpointed past a given trail file.
  • Watch for long-running source transactions that can hold up checkpoint advancement and inflate apparent lag.

5Validation strategy

  • Reconcile row counts per table first — cheap, fast, and catches gross mismatches immediately.
  • Follow with checksum or hash-based comparison (e.g. Oracle GoldenGate Veridata, or a custom column-hash job) for data-level confidence beyond row counts.
  • Validate dependent objects too: sequences, identity columns, constraints, indexes, and materialized views — these don't always replicate automatically, especially cross-engine.

6Cutover & rollback planning

  • Rehearse the cutover runbook at least once in a non-production dry run, timing each step.
  • Keep the source available and consider enabling reverse CDC (target → source) immediately post-cutover as a fast, low-risk rollback path if issues surface.
  • Define an explicit go/no-go checklist (see the Live Simulator's cutover checklist) and a named decision-maker before the window opens.

iRepresentative migration scenarios

Composite, illustrative scenarios based on common patterns seen across GoldenGate migration engagements — useful as talking points for customer-facing conversations.

Core Banking: Zero-Downtime Move to OCI

Homogeneous · Oracle → Oracle Exadata Cloud (OCI) · Financial Services

A retail bank needed to retire an aging on-prem data center hosting its core banking platform without a service interruption customers would notice.

Challenge

24x7 transaction processing, regulatory uptime commitments, and a multi-terabyte database ruled out any planned outage window longer than a few minutes.

Approach

RMAN-based Initial Load in parallel with GoldenGate Integrated Extract capturing CDC from the outset; Parallel Replicat applied the catch-up backlog against the OCI Exadata target.

GG components

Integrated Extract, Parallel Replicat (integrated mode), trail encryption over FastConnect, GoldenGate Veridata for reconciliation.

Outcome

Cutover window held under five minutes; reverse CDC ran for two weeks post-cutover as a rollback safety net before the source was decommissioned.

Retail: Heterogeneous Cost-Optimization Migration

Heterogeneous · Microsoft SQL Server → PostgreSQL · Retail

A retailer wanted to move a large order-management database off costly proprietary licensing onto open-source PostgreSQL without disrupting order processing during peak season.

Challenge

Datatype and identity-column differences between engines, plus stored-procedure logic that had no direct PostgreSQL equivalent and needed rewriting.

Approach

Schema conversion tooling handled DDL translation up front; GoldenGate Extract captured SQL Server CDC while a native bulk export/import moved historical data, with column-level datatype mapping configured in Replicat.

GG components

Log-based Extract on SQL Server, file-based Initial Load, Replicat column mapping and datatype conversion functions.

Outcome

Migration completed outside peak season with a single-hour cutover window; ongoing licensing costs dropped materially post-migration.

Telecom: Analytics Offload to the Cloud

Data Warehouse · Oracle OLTP → Snowflake · Telecommunications

A telecom operator needed near-real-time customer usage data in Snowflake for analytics, without adding reporting load to the operational Oracle database.

Challenge

Reporting queries were competing with OLTP workload on the source, and batch ETL windows couldn't keep pace with the desired analytics freshness.

Approach

GoldenGate replicated continuously into a Snowflake landing layer; downstream dbt models transformed landing data into curated analytics tables on Snowflake's own schedule, decoupled from replication.

GG components

Integrated Extract, Replicat delivering to Snowflake staging tables only (no transformation in the replication path).

Outcome

Analytics freshness improved from a nightly batch to minutes, with zero measurable impact on OLTP source performance.

Insurance: Multi-Region Cloud Migration with Rollback Safety Net

Homogeneous · Oracle on-prem → OCI (multi-region) · Insurance

An insurer migrating policy-management systems to a new cloud region needed a conservative rollback story given strict regulatory and audit requirements.

Challenge

Any post-cutover data issue had to be reversible without data loss, and auditors required evidence that source and target stayed reconciled throughout.

Approach

Standard Initial Load + CDC catch-up, but cutover was staged behind a full validation sign-off gate, and bidirectional replication was pre-configured (using the patterns from the Bi-Directional Replication module) so the source could resume as primary within minutes if needed.

GG components

Integrated Extract/Replicat pair each direction, Auto CDR pre-armed but inactive until fallback triggered, row-count and checksum validation reports archived for audit.

Outcome

Cutover proceeded without incident; the pre-armed fallback path was never invoked but satisfied the audit requirement for a tested reversible migration.
