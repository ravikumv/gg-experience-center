What is a GoldenGate Filter?

A Oracle GoldenGate filter is a condition attached to a TABLE statement (in the Extract parameter file) or a MAP statement (in the Replicat parameter file) that decides which rows and which columns of a captured change actually make it downstream. Nothing is filtered by magic — every filter is plain text sitting inside a parameter file, evaluated row-by-row as GoldenGate processes the change stream.

Filtering answers two independent questions for every operation GoldenGate touches: “should this row go through at all?” (row selection) and “which of its columns should travel?” (column selection). The two are combined freely in the same TABLE/MAP statement.

Think of it as — a mail-sorting facility. The WHERE/FILTER clause is the sorter deciding which envelopes even leave the building; COLS/COLSEXCEPT is someone redacting specific lines on the envelopes that are allowed through. Where in the pipeline that sorting desk sits — at the source post office (Extract) or at the destination office (Replicat) — is exactly the Option A / Option B choice explored later in this simulator.

Why filter at all? — Purpose

Reduce volume. Dropping irrelevant rows/columns early shrinks trail files, network transfer, and target storage.

Protect sensitive data. Column filtering (COLSEXCEPT) can keep a PII or financial column out of the trail entirely, rather than masking it after the fact.

Selective replication. Send only the rows a target actually needs — e.g. one region to one target, another region to a different target.

Split workload. The @RANGE function divides one table's changes across several parallel Replicat threads/groups by key range.

Exception handling. RAISEERROR on a failed FILTER can reroute a row to an exceptions table instead of silently dropping it.

Where can a filter live?

LocationParameter fileTypical use
TABLE statementExtract .prmFilter at the source, before the trail is ever written
MAP statementReplicat .prmFilter at apply time, after the trail already has the data
TABLE (pass-through)Data-pump Extract .prmRare; usually pass-through only, no re-filtering

This dual placement — source-side vs target-side — is the entire premise of the Option A / Option B live simulators in tabs 4 and 5.

WHERE vs FILTER — the quick answer

WHERE — simple. Basic comparison operators only (=, <>, >, >=, <, <=), combined with AND/OR. Good for straightforward row selection on any data type, including strings.

FILTER — complex. Everything WHERE can do, plus the full Oracle GoldenGate column-conversion function library (@COMPUTE, @STREQ, @RANGE, arithmetic, and more), plus ON INSERT/UPDATE/DELETE and IGNORE INSERT/UPDATE/DELETE operation-type controls, plus RAISEERROR in MAP.

A prerequisite people forget

Filtering can only evaluate columns that Oracle GoldenGate actually has access to. In a TRANLOG Extract that means columns present in the redo log; anything else must be explicitly pulled in with FETCHCOLS.

In the Extract pump and in Replicat, a column must be present in the trail file to be filterable there. So any column you plan to reference in a WHERE/FILTER clause must be logged with ADD TRANDATA COLS, keeping the default of LOGALLSUPCOLS.

Types of filters — at a glance

Row filters

WHEREFILTER

Decide whether an entire operation (row change) is kept or dropped. Evaluated per-row, per-operation.

Column filters

COLSCOLSEXCEPT

Decide which columns of a kept row are actually captured. Extract/pump only — not a Replicat option.

Operation-type filters

ON INSERT/UPDATE/DELETEIGNORE ...

Restrict a FILTER clause (or an entire TABLE/MAP) to specific SQL operation types.

Function-based filters

@COMPUTE@STREQ@RANGE

FILTER-only. Column-conversion functions let you test computed values, string equality, or split workload by key range.

Exception routing

RAISEERROREXCEPTIONSONLY

MAP-only. On filter failure, raise a user-defined error and route the row to an exceptions MAP instead of silently dropping it.

Workload-splitting filters

@RANGE (n, total, key)

Used inside FILTER to divide one table's changes across multiple parallel Replicat groups/threads by key range.

SQLEXEC-based filters

SQLEXECBEFOREFILTER@GETVAL

The most powerful tier. A subquery or stored procedure runs before the FILTER clause is evaluated (BEFOREFILTER), and FILTER then tests the value it returned. Works identically on the Extract TABLE statement or the Replicat MAP statement — see the Filter Complexity Ladder in the Syntax Reference tab.

Oracle GoldenGate does not support filtering, column mapping, or manipulation of LOB (large object) columns, and FILTER is not supported for columns containing multi-byte character truncation cases — check the documentation for the current list of restrictions before designing a filter strategy.

Filter Complexity Ladder — Normal → Simple → Medium → Complex

Each tier below shows both placements: the Extract-side TABLE statement and its Replicat-side MAP equivalent — the same complexity ladder applies whichever side you filter on.

NORMAL

Extracts all data without any conditions.

EXTRACT · TABLE

TABLE GL.GL_JE_BATCHES;

REPLICAT · MAP

MAP GL.GL_JE_BATCHES,
  TARGET GL.GL_JE_BATCHES;

SIMPLE

Filter Condition using WHERE clause — a direct WHERE condition filters records.

EXTRACT · TABLE

TABLE GL.GL_JE_BATCHES,
  WHERE (JE_BATCH_ID = 8970);

REPLICAT · MAP

MAP GL.GL_JE_BATCHES,
  TARGET GL.GL_JE_BATCHES,
  WHERE (JE_BATCH_ID = 8970);

MEDIUM

Filter Condition with Sub-Query (SQLEXEC) — a subquery checks a condition before the row is filtered.

EXTRACT · TABLE

TABLE GL.GL_JE_BATCHES,
  KEYCOLS (JE_BATCH_ID),
  SQLEXEC (ID lookup_batch,
    QUERY 'select count(*) output
           from GL.GL_JE_HEADERS
           where JE_BATCH_ID=:VAR_1
           and STATUS=''P''',
    PARAMS (VAR_1 = @BEFORE (JE_BATCH_ID)),
    BEFOREFILTER),
  FILTER (lookup_batch.output > 0);

REPLICAT · MAP

MAP GL.GL_JE_BATCHES,
  TARGET GL.GL_JE_BATCHES,
  SQLEXEC (ID lookup_batch,
    QUERY 'select count(*) output
           from GL.GL_JE_HEADERS
           where JE_BATCH_ID=:VAR_1
           and STATUS=''P''',
    PARAMS (VAR_1 = JE_BATCH_ID),
    BEFOREFILTER),
  FILTER (lookup_batch.output > 0);

COMPLEX

Filter Condition using Stored Procedure — a stored procedure is called to decide whether the row is filtered.

EXTRACT · TABLE

TABLE STAT.FAORDER_LOG,
  SQLEXEC (SPNAME STAT.GG_FILTER_COND_PRC,
    ID DBSP_FAORDER_LOG,
    PARAMS (P_TABLE_NAME = 'FAORDER_LOG',
            P_KEY_VALUE1 = ID),
    BEFOREFILTER),
  FILTER (@GETVAL (DBSP_FAORDER_LOG.P_COUNT_VAL) > 0);

REPLICAT · MAP

MAP STAT.FAORDER_LOG,
  TARGET STAT.FAORDER_LOG,
  SQLEXEC (SPNAME STAT.GG_FILTER_COND_PRC,
    ID DBSP_FAORDER_LOG,
    PARAMS (P_TABLE_NAME = 'FAORDER_LOG',
            P_KEY_VALUE1 = ID),
    BEFOREFILTER),
  FILTER (@GETVAL (DBSP_FAORDER_LOG.P_COUNT_VAL) > 0);

Reading the Medium example

KEYCOLS (JE_BATCH_ID) declares the key GoldenGate uses for the lookup. SQLEXEC runs a named query (ID lookup_batch) that counts pending (STATUS='P') header rows for the batch. On the Extract side, PARAMS (VAR_1 = @BEFORE (JE_BATCH_ID)) binds :VAR_1 to the row's before-image key value; on the Replicat side, the trail already carries the column, so the MAP statement binds it directly with PARAMS (VAR_1 = JE_BATCH_ID). BEFOREFILTER forces the query to run before FILTER is evaluated, so FILTER (lookup_batch.output > 0) can test the returned count — identically on either side.

Reading the Complex example

SQLEXEC (SPNAME ...) calls a database stored procedure instead of an inline query — useful when the filtering logic is already encapsulated in PL/SQL. PARAMS passes the table name and key value into the procedure's IN parameters. BEFOREFILTER again guarantees the procedure runs first, and @GETVAL (DBSP_FAORDER_LOG.P_COUNT_VAL) retrieves the procedure's OUT parameter for FILTER to test. On Replicat, the stored procedure must exist in the target database (it runs where the MAP statement executes), whereas on Extract it must exist in the source database.

Both Medium and Complex tiers add a database round-trip per row (a query or a procedure call) before the FILTER decision. That's real overhead per operation — reserve them for cases the WHERE/FILTER-only tiers genuinely can't express, such as checking a related table's state or reusing existing PL/SQL business logic.

Detailed clause-by-clause reference

1) WHERE clause — simple row selection

Enclosed in parentheses; literals in single quotes. Accepts basic comparison operators and AND/OR.

TABLE HR.EMPLOYEES,
  WHERE (REGION = 'WEST');

MAP HR.EMPLOYEES, TARGET HR.EMPLOYEES,
  WHERE (SALARY > 50000);

2) FILTER clause — complex row selection

Supports numeric comparisons, arithmetic operators, column-conversion functions, and operation-type qualifiers.

TABLE ACT.TCUSTORD,
  FILTER (ON UPDATE, ON DELETE, AMOUNT > 50);

MAP SALES.TCUSTORD, TARGET SALES.TORD,
  FILTER (@COMPUTE (PRICE * QTY) > 10000);

3) COLS / COLSEXCEPT — column selection

Extract-side (TABLE) only. COLS whitelists columns to capture; COLSEXCEPT blacklists columns to drop. Key columns must never be excluded. If used on the primary Extract rather than the pump, add PASSTHRU on the pump.

TABLE FIN.ACCOUNTS,
  COLSEXCEPT (SSN, CVV);

TABLE FIN.ACCOUNTS,
  COLS (ACCT_ID, CUST_NAME, REGION, AMOUNT);

4) RAISEERROR — exception routing (MAP only)

When a FILTER fails, raise a user-defined error and route the row through REPERROR to an exceptions MAP instead of dropping it silently.

REPERROR (9999, EXCEPTION)
MAP OWNER.SRCTAB, TARGET OWNER.TARGTAB,
  FILTER (BALANCE > 15000, RAISEERROR 9999);

MAP OWNER.SRCTAB, TARGET OWNER.TARGEXC,
  EXCEPTIONSONLY,
  COLMAP (USEDEFAULTS, ERRTYPE = 'FILTER FAILED');

5) @RANGE — splitting workload

Distributes one table's changes across multiple parallel MAP/TABLE statements (and therefore multiple Replicat groups or threads) by key range.

-- Replicat group 1 parameter file
MAP sales.acct, TARGET sales.acct, FILTER (@RANGE (1, 2, ID));

-- Replicat group 2 parameter file
MAP sales.acct, TARGET sales.acct, FILTER (@RANGE (2, 2, ID));

6) @STREQ — string equality inside FILTER

WHERE handles string comparisons natively; FILTER needs a string function such as @STREQ since its native comparisons are numeric.

TABLE ACCT.TCUSTORD,
  FILTER (@STREQ ("NAME", 'JOE') > 0);

7) SQLEXEC + BEFOREFILTER — subquery-driven filter (Medium tier)

Runs an inline query per row before FILTER evaluates it — used when the pass/fail decision depends on the state of a related table. Valid in both TABLE (Extract) and MAP (Replicat).

EXTRACT · TABLE

TABLE GL.GL_JE_BATCHES,
  KEYCOLS (JE_BATCH_ID),
  SQLEXEC (ID lookup_batch,
    QUERY 'select count(*) output from
           GL.GL_JE_HEADERS where
           JE_BATCH_ID=:VAR_1 and STATUS=''P''',
    PARAMS (VAR_1 = @BEFORE (JE_BATCH_ID)),
    BEFOREFILTER),
  FILTER (lookup_batch.output > 0);

REPLICAT · MAP

MAP GL.GL_JE_BATCHES, TARGET GL.GL_JE_BATCHES,
  SQLEXEC (ID lookup_batch,
    QUERY 'select count(*) output from
           GL.GL_JE_HEADERS where
           JE_BATCH_ID=:VAR_1 and STATUS=''P''',
    PARAMS (VAR_1 = JE_BATCH_ID),
    BEFOREFILTER),
  FILTER (lookup_batch.output > 0);

8) SQLEXEC (SPNAME) + @GETVAL — stored-procedure filter (Complex tier)

Calls an existing PL/SQL stored procedure to make the filtering decision, then reads its OUT parameter with @GETVAL. Valid in both TABLE (Extract) and MAP (Replicat) — the procedure must exist in whichever database that statement runs against.

EXTRACT · TABLE

TABLE STAT.FAORDER_LOG,
  SQLEXEC (SPNAME STAT.GG_FILTER_COND_PRC,
    ID DBSP_FAORDER_LOG,
    PARAMS (P_TABLE_NAME = 'FAORDER_LOG',
            P_KEY_VALUE1 = ID),
    BEFOREFILTER),
  FILTER (@GETVAL (DBSP_FAORDER_LOG.P_COUNT_VAL) > 0);

REPLICAT · MAP

MAP STAT.FAORDER_LOG, TARGET STAT.FAORDER_LOG,
  SQLEXEC (SPNAME STAT.GG_FILTER_COND_PRC,
    ID DBSP_FAORDER_LOG,
    PARAMS (P_TABLE_NAME = 'FAORDER_LOG',
            P_KEY_VALUE1 = ID),
    BEFOREFILTER),
  FILTER (@GETVAL (DBSP_FAORDER_LOG.P_COUNT_VAL) > 0);

Do's

ADD TRANDATA COLS first — a column must be explicitly logged (and present in the trail) before any WHERE/FILTER/COLS clause can reference it.

Keep key columns in COLS — primary/unique key columns (or KEYCOLS) must remain in the column list or capture fails with an error.

Use FILTER for anything numeric/complex — @COMPUTE, arithmetic, and @RANGE only work inside FILTER.

Chain multiple FILTERs deliberately — GoldenGate evaluates them in the order listed; if one fails, they all fail.

Use BEFOREFILTER with SQLEXEC — it guarantees the subquery/stored-procedure result is available before FILTER tries to read it.

Don'ts

Don't use FILTER for plain string equality — its native operators are numeric; use WHERE or a string function like @STREQ instead.

Don't COLSEXCEPT a key column — and don't use it to drop unsupported data types; it won't exclude those anyway.

Don't expect LOB filtering — large object columns are not supported for filtering, mapping, or manipulation.

Don't forget PASSTHRU — if COLS/COLSEXCEPT is set on the primary Extract rather than the pump, the pump needs PASSTHRU to avoid re-evaluating column rules.

Don't reach for SQLEXEC by default — it costs a database round-trip per row; use it only when WHERE/FILTER alone truly cannot express the condition.

Option A vs Option B — Comparison & Best Practices

  
Same filter condition, two different places to enforce it. Neither is universally “better” — the right choice depends on what else needs the trail.


  

    
DimensionOption A — Filter at Extract (source)Option B — Filter at Replicat (target)

    
Trail file sizeSmaller — only qualifying rows writtenLarger — every captured row written

    
Network / WAN transferLower — rejected rows never leave sourceHigher — every row crosses the network

    
Reusability of trail for other consumersLimited — dropped rows are gone for goodFull — other Replicats/audits can still see everything

    
Best for regulated / sensitive columnsYes — COLSEXCEPT keeps data from ever leaving sourceOnly if masking happens before the trail is shared further

    
Centralized filter logic across many targetsMust be duplicated per Extract/TABLE statementEasier — each MAP can apply its own rule from one trail

    
Where to reference the filtered columnMust be in the redo log / logged via ADD TRANDATA COLSMust be present in the trail file

  


  

    

      
Choose Option A when…

      
A column must never physically leave the source environment (PII, payment data, cross-border data residency rules); the trail has exactly one downstream consumer; or minimizing WAN bandwidth for a remote/cloud target is the priority.

    

    

      
Choose Option B when…

      
The same trail feeds multiple targets or an audit/replay process that each need different subsets; filter rules change often and you don't want to bounce the primary Extract; or you want to use RAISEERROR to route rejected rows to an exceptions table rather than lose them.

    

  


  
A practical field note echoed across GoldenGate implementations: put the FILTER in the Replicat (Option B) when the trail may be needed for other targets later — it's far cheaper to add a second Replicat reading an existing full trail than to reprocess history through a re-tuned Extract. Reserve Extract-side filtering (Option A) for cases where the data genuinely must never be captured in the first place.


  

    
Remember the shared prerequisite

    
Whichever option you pick, a column can only be filtered on if Oracle GoldenGate can see it: logged in the redo log and captured via ADD TRANDATA COLS with LOGALLSUPCOLS retained, and present in the trail by the time it reaches the stage doing the filtering.
