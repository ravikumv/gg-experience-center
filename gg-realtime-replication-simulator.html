Data Replication Overview

Oracle GoldenGate captures committed transactions from a source database's redo/transaction logs the moment they occur, and applies them to one or more target databases with sub-second latency — without relying on triggers or heavy source-side overhead. Because capture reads log records rather than querying tables, replication has minimal impact on production workloads.

This makes GoldenGate the foundation for real-time analytics, zero-downtime migration, high availability & DR, active-active systems, and heterogeneous cross-platform replication — all explored across the tabs in this simulator.

Think of it as — a courier reading a package manifest the instant it's stamped, rather than periodically walking the warehouse checking for new boxes. The manifest (redo log) is read once, in order, and the courier (Extract) never touches the shelves (tables) themselves — which is exactly why the overhead on the source system stays so low.

The Replication Path, In Short

Extract reads committed changes from the source's redo/transaction logs and writes them to a Trail file in a database-independent format. The trail is shipped over the network to the target, where Replicat reads it and applies the changes to the target database — continuously, in the order transactions committed. Explore the full animated flow in the Architecture tab, or trigger live transactions yourself in the Live Transaction Simulator.

Core Concepts

Twelve foundational building blocks every GoldenGate implementation relies on.

📝

Supplemental Logging

Redo logs normally contain only changed columns. Supplemental logging forces Oracle to also log key/unique-index column values for updated rows, so Extract has enough information to uniquely identify each row on the target — essential for UPDATE and DELETE operations.

ALTER TABLE hr.employees ADD SUPPLEMENTAL LOG DATA (PRIMARY KEY, UNIQUE INDEX) COLUMNS;
🎯

Trandata

Table-level logging enabled via GGSCI's ADD TRANDATA — the operational counterpart to database-level supplemental logging. It marks individual tables (or a whole schema with SCHEMATRANDATA) so Extract captures the key columns it needs for each one, and is the standard method for non-Oracle sources.

GGSCI> DBLOGIN USERIDALIAS ora_src GGSCI> ADD TRANDATA hr.employees GGSCI> ADD SCHEMATRANDATA hr ALLCOLS
🗃️

Archive Logging

The source database must run in ARCHIVELOG mode so that redo logs are preserved after being overwritten online. Integrated Extract in particular depends on archived logs to catch up if it falls behind or is restarted.

SELECT log_mode FROM v$database; -- must return ARCHIVELOG
🔐

Credential Store

A secure wallet (CREDENTIALSTORE) that holds database and admin credentials as encrypted aliases, so parameter files reference an alias instead of a plaintext username/password — meeting security and audit requirements.

ADD CREDENTIALSTORE ALTER CREDENTIALSTORE ADD USER ggadmin@orclpdb1 ALIAS ora_src
💓

Heartbeat Tables

Small system tables that GoldenGate updates on a timer and replicates end-to-end through the same pipeline as user data, allowing accurate end-to-end lag measurement even when there's no application activity.

GGSCI> ADD HEARTBEATTABLE
📍

Checkpoint Tables / Files

Extract and Replicat persist their exact read/write position (trail file + RBA offset) to checkpoints, so after a restart or failover processing resumes exactly where it left off — with no data loss or duplication.

GGSCI> INFO REPLICAT rep1, DETAIL Checkpoint: seqno 000000123, rba 45021088
📂

Trail Management

Trail files store captured changes in a compact, database-independent format. Purging policy, file size, and retention are tuned to balance disk usage against the ability to reprocess history after an outage.

ADD EXTTRAIL /ogg/dirdat/lt, EXTRACT ext1, MEGABYTES 500 PURGE OLDEXTRACTS /ogg/dirdat/lt*, USECHECKPOINTS, MINKEEPHOURS 24
⚔️

Conflict Detection & Resolution

In bi-directional/active-active topologies, the same row can change on both sides near-simultaneously. CDR detects these collisions and resolves them automatically using configurable rules such as latest-timestamp-wins or site-priority.

MAP src.orders, TARGET tgt.orders, COLSEXCEPT(row_ts), RESOLUTIONS ( (INSERTROWEXISTS, OVERWRITE));
🏛️

DDL Replication

GoldenGate can capture and replicate schema changes — CREATE, ALTER, DROP — alongside data changes, keeping target structures in sync automatically instead of requiring manual DDL coordination.

GGSCI> DBLOGIN USERIDALIAS ora_src GGSCI> ADD SCHEMATRANDATA hr -- extract param: DDL INCLUDE MAPPED
⚙️

Parameter Files

Extract, Replicat, and the Manager are each configured through plain-text parameter files (.prm) that define what to capture, where trails live, mapping rules, filters, and runtime behavior — the operational contract for every process.

EXTRACT ext1 USERIDALIAS ora_src EXTTRAIL /ogg/dirdat/lt TABLE hr.employees;
🔒

Compression & Encryption

Trail data can be compressed to reduce network bandwidth and encrypted in transit (and at rest) to meet security requirements — configured at the Distribution Path level without changing capture or apply logic.

ALTER DISTPATH path1, COMPRESSION ENABLED ALTER DISTPATH path1, ENCRYPT ENABLED
🧵

Coordinated / Parallel Replicat

Instead of a single apply thread, Coordinated Replicat splits work across multiple parallel threads by key range, dramatically increasing apply throughput for high-volume targets while preserving transactional integrity.

ADD REPLICAT rep1, COORDINATED EXTTRAIL /ogg/dirdat/rt, THREADS 8

Initial Load vs. Continuous Data Capture

Two distinct phases of a GoldenGate implementation — compare how each moves data.

Initial Load — Bulk Baseline Sync

Moves the existing, historical data set from source to target once, in parallel bulk streams, before CDC takes over for ongoing changes.

🗄️Source TableFull Data Set
🗄️Target TableBeing Loaded

How It Works

  • Uses direct bulk-load methods (e.g. Oracle Data Pump, direct path load, or GoldenGate's own file-to-database load) — not the trail pipeline.
  • Runs in parallel across multiple threads/tables to move large volumes quickly.
  • Captures a defined SCN/checkpoint at load start so CDC can pick up exactly from that point with no gap or duplication.

When It's Used

  • First-time synchronization before enabling ongoing replication.
  • Re-instantiating a target after extended downtime.
  • Migrations where the target must match source state at a single point in time.

Continuous Data Capture — Ongoing Replication

After the initial load completes, CDC captures every subsequent committed change from the redo stream and applies it continuously, keeping source and target in sync in real time.

📜Redo Logs
⚙️Extract
📁Trail
⚙️Replicat
🗄️Target

How It Works

  • Extract reads committed transactions from redo/archive logs continuously — no polling, no triggers.
  • Changes flow through the trail pipeline and are applied by Replicat, typically within sub-second to a few seconds.
  • Checkpoints ensure exactly-once delivery even across restarts.

When It's Used

  • Ongoing steady-state replication for HA/DR, reporting, or active-active systems.
  • Feeding real-time analytics and data lakes/warehouses.
  • Any scenario requiring near-zero replication lag after the initial baseline is in place.
