Replication Lag — where is the time actually going?

“Lag” is not one thing. It is the sum of time spent at each stage between a commit on the source and that same change becoming visible on the target. The single most important troubleshooting skill is not fixing lag — it is isolating which stage owns it before making any change.

Think of it as — a parcel moving through a courier network: pickup (Extract), regional sorting hub (Trail/Distribution), highway transit (Network), local depot (Receiver), and final delivery (Replicat). A parcel can be “late” at any single hop — you have to check each scan point, not just the final delivery time, to know which hop is slow.

Lag types & contributing factors — at a glance

Extract Lag

Delay between a source commit and Extract writing the corresponding record to the trail. Usually reflects how far behind Extract is in mining the redo/WAL stream.

Trail Lag

Time a record spends sitting in the local trail before Distribution Service picks it up. Often small, but grows if Distribution is stalled or the trail is on slow storage.

Distribution Lag

Time to ship trail data across the network to the remote (target-side) trail. Grows with bandwidth constraints, WAN latency, or Distribution Service problems.

Network Lag

Pure transport delay — latency, packet loss, throughput ceilings, firewall/proxy inspection overhead — between source and target GoldenGate deployments.

Replicat Lag

Delay between a record arriving in the remote trail and Replicat successfully applying (and committing) it on the target. The most common lag source in practice.

Target Database Performance

Target-side waits — contention, slow I/O, missing indexes, undo pressure, resource limits — that make each apply operation take longer, backing up Replicat.

Long Transactions

A transaction open for a long time on the source cannot be written to the trail (or applied) until it commits or rolls back; Extract/Replicat must hold it in memory or spill to disk.

High Transaction Volume

Sustained high change rate can outpace a single Extract or Replicat thread's capacity, causing lag to climb even when every individual component is “healthy.”

Apply Bottleneck

Serialized or conflict-heavy apply (e.g. hot rows, foreign-key dependency ordering) that prevents Replicat from parallelizing effectively, even with parallelism enabled.

How to identify where the lag is occurring

Step 1 — Compare checkpoints, not just “lag”

Run INFO EXTRACT <name>, DETAIL and INFO REPLICAT <name>, DETAIL (or the equivalent Microservices REST/Admin Server calls). Compare “At Checkpoint” timestamps against “Time Since Chkpt” to see which process's checkpoint is furthest behind current time.

Step 2 — Split source-side vs target-side

If Extract lag is low but Replicat lag is high, the problem is on the target/apply side. If Extract lag itself is high, the problem is on the source (redo generation rate, mining overhead, or long-running transactions).

Step 3 — Check the trail growth rate

A rapidly growing local trail with low Extract lag but high Distribution/Replicat lag points downstream. A rapidly growing trail with high Extract lag points to redo mining being the bottleneck.

Step 4 — Correlate with a known event

Batch jobs, month-end processing, a missing index deployed on target, or a network change are common lag triggers. Compare the lag onset time to change/maintenance windows before assuming a GoldenGate defect.

Lag figures reported by GoldenGate reflect checkpoint progress, not necessarily wall-clock “user-visible” delay. Always corroborate with source and target database time, not GoldenGate output alone, when the discrepancy matters operationally.

Trail Troubleshooting

The trail is the durable, on-disk record between Extract and Replicat. Most “replication stopped” incidents trace back to a trail problem: missing files, a full mount point, or a broken path reference.

Trail File Missing

SymptomExtract or Replicat abends referencing a sequence number that cannot be found; INFO shows a gap between expected and actual trail sequence.
CauseTrail file deleted manually, purged by a retention/cleanup job before it was fully processed, or lost due to a storage failure.
CheckCompare the sequence number in the error against files actually present in the trail directory; check PURGEOLDEXTRACTS / housekeeping job history and storage/OS logs for deletions.
FixIf the file is truly gone and cannot be restored from backup, the reading process must be repositioned past the gap (data loss risk) or the pipeline rebuilt from a fresh instantiation/initial load.
ValidationINFO EXTRACT/REPLICAT shows a clean, advancing checkpoint with no further “file not found” errors; reconcile row counts on source/target after recovery.

Trail File Growing (unbounded)

SymptomLocal or remote trail directory size climbs continuously; disk usage alerts fire; Replicat lag increases in parallel.
CauseDownstream Replicat (or Distribution/Receiver) is not consuming the trail as fast as Extract writes it — a stalled, slow, or stopped Replicat is the most common cause.
CheckINFO REPLICAT for status/lag; confirm Replicat is actually RUNNING and not looping on an error; check apply-side database health.
FixResolve the apply-side bottleneck or error causing Replicat to fall behind or stop; once Replicat catches up, trail growth stabilizes and old files age out per retention.
ValidationTrail directory size stabilizes or shrinks; Replicat checkpoint advances at a rate matching Extract's write rate.

Trail Directory Full / Disk Space Issues

SymptomExtract abends with an I/O or “no space left on device” style error when attempting to write the next trail file.
CauseMount point hosting the trail directory is undersized, retention is too generous for the change volume, or an unrelated process is consuming the same filesystem.
CheckOS-level disk usage (df -h on the trail mount); trail retention settings (PURGEOLDEXTRACTS); growth trend over recent days.
FixFree space immediately (purge already-processed old trail files if safe), then correct the root cause: extend storage, tighten retention, or move the trail to dedicated storage.
ValidationExtract restarts and writes successfully; free space monitoring shows sustainable headroom given the current change rate.

Incorrect Trail Path

SymptomProcess fails to start, or GGSCI ADD EXTTRAIL/ADD RMTTRAIL commands reference a directory that does not resolve on the target host.
CauseParameter file references a trail path/prefix that was moved, mistyped, or never created; mismatch between Classic and Microservices deployment directory conventions.
CheckCompare EXTTRAIL/RMTTRAIL parameter values against actual deployment directory structure; check GGSCI INFO EXTRAIL/INFO RMTTRAIL.
FixCorrect the path in the parameter file or recreate the trail definition with the right path; ensure the directory exists and the GoldenGate OS user has read/write permission.
ValidationProcess starts cleanly and begins writing to/reading from the expected directory.

Trail Sequence Issues

SymptomCheckpoint references a sequence number that does not match what is physically present, or sequence numbers appear to jump/skip.
CauseManual trail file manipulation, a botched trail rollover, or checkpoint corruption after an unclean process termination.
CheckINFO EXTRACT/REPLICAT, DETAIL for checkpoint sequence vs. files on disk; process report for the exact abend message.
FixIn most cases this requires Oracle Support engagement or a checkpoint reset to a known-good position; a full re-instantiation may be safer than guessing at a manual reposition.
ValidationProcess starts and checkpoint sequence advances consistently with no further sequence-mismatch errors.

Remote Trail Issues

SymptomDistribution Service reports failures delivering to the remote (target-side) trail; Receiver Service errors on write; remote trail not growing despite local trail growth.
CauseNetwork interruption, Receiver Service down or unreachable, target-side disk full, or a certificate/authentication failure between Distribution and Receiver.
CheckDistribution Service and Receiver Service status/logs; network connectivity between deployments; target-side disk space.
FixRestore network/service connectivity, free target-side disk space, or correct the security configuration blocking the connection (see Security Troubleshooting).
ValidationRemote trail resumes growing in step with the local trail; Distribution Service reports a healthy, low-latency delivery status.

Trail Retention

SymptomEither trail files accumulate indefinitely (disk pressure) or files are purged before every consuming process has finished with them (data-loss risk on recovery).
CauseRetention parameters not tuned to the environment — too loose (unbounded growth) or too aggressive (purged before a lagging Replicat or a required recovery window has used them).
CheckPURGEOLDEXTRACTS settings in the GLOBALS/parameter file; compare retention window against the worst-case observed Replicat lag and any recovery/DR requirements.
FixSet retention (age- or count-based) to comfortably exceed the maximum expected lag plus a safety margin, balanced against available storage.
ValidationDisk usage trends flat over time under steady-state load, and no process ever references a sequence number that has already been purged.
Trail problems are frequently a symptom of a lag problem (see the Replication Lag tab) rather than an independent root cause — a trail that is “full” or “growing” is very often just downstream of a stalled Replicat or a network bottleneck.

Relevant GoldenGate concepts

Tuning is workload- and environment-dependent. There is no universal production value for any of these parameters — the descriptions below explain purpose and monitoring signals, not target settings.

MAP_PARALLELISM

Purpose: Controls how many parallel apply threads/processes a Parallel Replicat can use for a given mapping.
When relevant: Apply-side throughput is the bottleneck and target dependency ordering permits parallel apply.
Monitor: Replicat lag trend, target CPU/session count, and apply conflicts/errors after any change.
Potential impact: Higher parallelism can raise throughput but also raise contention risk on the target; must be balanced against target capacity.

APPLY_PARALLELISM

Purpose: Governs the degree of parallel apply within a Parallel Replicat's overall processing model.
When relevant: Similar to MAP_PARALLELISM — used when apply throughput, not capture or network, is the limiting factor.
Monitor: Thread/worker utilization, apply error rate, target resource consumption.
Potential impact: Improves throughput ceiling when target and workload characteristics support parallel apply; can worsen contention if the workload is highly conflict-prone.

SPLIT_TRANS_RECS

Purpose: Relates to how large transactions can be split for processing rather than handled as one monolithic unit.
When relevant: Very large transactions are causing memory pressure or serialized, single-threaded apply behavior.
Monitor: Memory/cache usage during large transactions, apply latency spikes coinciding with large batch jobs.
Potential impact: Can help large transactions move through the pipeline more smoothly, but interacts with transaction ordering guarantees and requires careful validation.

GROUPTRANSOPS

Purpose: Controls how many source operations Replicat groups together into a single target transaction when using grouped/batched apply.
When relevant: High operation volume where transaction-per-operation apply overhead (commit frequency) is limiting throughput.
Monitor: Apply throughput, target redo/commit rate, latency of individual grouped commits.
Potential impact: Larger grouping can raise throughput but increases the amount of work that must be redone/rolled back on a single apply failure.

MAXTRANSOPS

Purpose: Caps the number of operations Extract holds for a single source transaction before writing/handling it differently.
When relevant: Extremely large source transactions risk exhausting memory or causing outsized trail writes.
Monitor: Extract memory usage, warnings/errors related to oversized transactions.
Potential impact: Protects Extract stability for outlier transactions, but the right threshold depends entirely on typical vs. outlier transaction sizes in the workload.

CACHEMGR

Purpose: Oracle GoldenGate's memory/cache manager used by Extract and Replicat to buffer transaction data, spilling to disk when memory limits are reached.
When relevant: Long-running or large transactions accumulate significant in-flight data before commit.
Monitor: Cache statistics in the process report (cache used, paged-out volume), disk I/O on the cache spill directory.
Potential impact: Insufficient cache sizing for the workload leads to excessive disk paging, which itself becomes a performance bottleneck.

WARNLONGTRANS

Purpose: Issues a warning when a transaction has been open longer than a specified threshold, surfacing long-running transactions early.
When relevant: Diagnosing lag or trail growth suspected to be caused by long-open source transactions.
Monitor: Warning messages in the Extract report, correlated against application/batch job schedules.
Potential impact: Purely diagnostic — does not change behavior, but is often the fastest way to confirm or rule out long transactions as a lag root cause.
These parameters interact with each other and with database-side settings. Changing one in isolation without measuring the effect on the others (and on the target database) is a common source of new problems. Tuning decisions should always be validated against the specific workload, hardware, and SLAs of the environment in question.

Security Troubleshooting

Security-related failures usually stop a process cold at startup or at connection time, rather than causing gradual degradation — making them easier to isolate once you know what to check.

Invalid Credentials

SymptomProcess abends immediately at startup, or DBLOGIN fails with a logon-denied style database error.
CauseWrong username/password, an expired database password, or a credential that was rotated in the database but not updated in GoldenGate's credential store/wallet.
CheckAttempt a manual database login with the same credentials outside GoldenGate; check password expiry policy on the account; verify which credential alias the parameter file actually references.
FixUpdate the password in the database and in the credential store (ALTER CREDENTIALSTORE or ADD USER ... ALIAS), keeping both in sync going forward.
ValidationManual DBLOGIN succeeds and the process starts and reaches RUNNING status without a security-related abend.

Missing Privileges

SymptomProcess starts but fails on a specific operation — registering Extract, reading redo, or writing to a target table — with a permissions-denied database error.
CauseThe GoldenGate database account lacks a required role/privilege (e.g. capture privileges on source, DML/DDL privileges on target, or access to GoldenGate administrative packages).
CheckCompare the account's granted privileges against the documented prerequisite privilege list for the GoldenGate version and capture/apply mode in use.
FixGrant the missing privilege(s) using the documented setup scripts or explicit GRANT statements, then retry the failed operation.
ValidationThe previously failing operation completes successfully and does not recur across a restart.

Credential Store Issues

SymptomProcess cannot resolve a USERIDALIAS reference; error indicates the credential store/wallet could not be opened or the alias could not be found.
CauseWallet file missing, corrupted, moved, or created under a different OS user than the one running GoldenGate; alias name typo between the wallet and the parameter file.
CheckINFO CREDENTIALSTORE in GGSCI; file permissions and ownership on the wallet directory (commonly dirwlt).
FixRecreate the wallet if corrupted (CREATE WALLET), re-add the credential alias, and confirm the OS user running GoldenGate has read access.
ValidationINFO CREDENTIALSTORE lists the expected alias, and a process referencing that alias starts cleanly.

TLS Failure

SymptomDistribution/Receiver Service (or REST API) connection fails during the TLS handshake; connection resets before data transfer begins.
CauseMismatched TLS versions/cipher suites between source and target deployments, an untrusted or misconfigured certificate chain, or TLS being enabled on one side but not the other.
CheckService logs on both Distribution and Receiver Service for the specific handshake failure reason; confirm TLS configuration is symmetric on both ends.
FixAlign TLS configuration (version, cipher suite, certificate trust) across both deployments per the Microservices security documentation.
ValidationDistribution Service establishes and maintains a stable connection to Receiver Service with no repeated handshake errors.

Certificate Expiry

SymptomA previously working TLS connection begins failing at a predictable point in time; error explicitly references certificate validity/expiration.
CauseThe TLS certificate used by a Microservices deployment (or an intermediate/CA certificate in the chain) has passed its expiration date.
CheckCertificate expiry date via the OS/keystore tooling for the deployment; whether the failure timing lines up with a known expiry date.
FixRenew and redeploy the certificate before expiry as part of routine operations; update the trust store on the peer side if the CA also changed.
ValidationConnection succeeds and the new certificate's validity window comfortably covers the operational period ahead.

Authentication Failure

SymptomREST API or Administration Server login is rejected; GGSCI/Microservices Web UI login fails despite what looks like a correct password.
CauseWrong GoldenGate administrative user, account locked after repeated failed attempts, or an identity/authentication provider (if integrated) rejecting the request.
CheckAdministration Server logs for the specific rejection reason; account lock status; any external identity provider configuration.
FixReset or unlock the administrative account, correct the credentials, or fix the identity provider integration as applicable.
ValidationLogin succeeds consistently and the account does not re-lock under normal use.

Database Security Configuration

SymptomIntermittent or environment-specific connection failures that don't reproduce with a simple credential check — e.g. only from certain hosts, or only after a security patch.
CauseDatabase-level restrictions such as listener/firewall ACLs, Database Vault / Unified Audit restrictions, or profile-level connection limits interacting with GoldenGate's connection pattern.
CheckListener and database alert logs at the time of failure; any recently changed security policies, ACLs, or Database Vault realms affecting the GoldenGate account.
FixWork with the DBA/security team to add the necessary exception or realm authorization for the GoldenGate account, scoped as narrowly as the security policy allows.
ValidationConnections succeed reliably across the affected hosts/paths with no recurrence of the intermittent failure.
Security troubleshooting should always be done in coordination with the database and security teams — the fix is frequently a policy or grant that GoldenGate administrators may not have authority to change unilaterally.

DDL Troubleshooting

DDL (schema change) replication has more moving parts than DML replication and is a common source of silent divergence between source and target if not actively monitored.

DDL Not Replicated

SymptomA schema change made on the source (new column, index, etc.) never appears on the target; subsequent DML referencing the new object fails or is silently mismatched.
Possible CauseDDL replication was never enabled for this configuration, the object is excluded by a DDL filter/scope, or the DDL trigger/metadata capture mechanism failed silently.
InvestigationConfirm DDL replication is enabled in the parameter file/GLOBALS; check the DDL history table (source) for whether the change was even captured; review DDL-related parameters (DDL, DDLOPTIONS) for scope restrictions.
ResolutionEnable/correct DDL replication configuration, then manually apply the missed DDL on the target and resynchronize before allowing further DML on the affected object.
ValidationA new test DDL change on the source now appears on the target within the expected latency.

DDL Filtering

SymptomSome DDL replicates but specific statement types (e.g. certain object types or operations) are consistently skipped.
Possible CauseAn explicit DDL INCLUDE/EXCLUDE or DDLOPTIONS filter scoped the replication to a subset of DDL operation types or object types.
InvestigationReview the exact DDL parameter clause for INCLUDE/EXCLUDE mapping and operation-type restrictions; check whether the filtered-out statement type was an intentional exclusion.
ResolutionAdjust the DDL filter scope if the exclusion was unintentional; if intentional, document it so future gaps aren't mistaken for defects.
ValidationDDL of the previously-excluded type now replicates as expected (if the change was intentional), with no unintended new inclusions.

Unsupported DDL

SymptomA specific DDL statement consistently fails to replicate or triggers an error referencing an unsupported operation/object type.
Possible CauseThe statement type, object type, or database feature involved is outside what GoldenGate DDL replication supports for the source/target combination and version in use.
InvestigationCheck the DDL support matrix/restrictions for the specific GoldenGate version and database types involved; reproduce the statement in isolation to confirm it is the actual trigger.
ResolutionApply that specific DDL manually on the target as a documented exception, or restructure the change (where feasible) into a supported equivalent.
ValidationTarget schema matches source after the manual application, and subsequent DML against the affected object replicates cleanly.

Target DDL Failure

SymptomReplicat abends or logs a DDL apply error when attempting to execute the replicated DDL statement on the target.
Possible CauseTarget object already exists in a conflicting state, insufficient privileges on target, or a target-specific syntax/feature incompatibility (especially in heterogeneous replication).
InvestigationRead the exact database error returned for the DDL apply attempt; compare current target object state against what the DDL statement expects to find.
ResolutionResolve the specific conflict (drop/adjust the conflicting object, grant privileges, or use DDLSUBST / DDLOPTIONS MAPPED to adapt syntax for heterogeneous targets), then reprocess the DDL.
ValidationTarget schema now matches the intended source-side change, and Replicat resumes normal apply of subsequent operations.

Schema Differences

SymptomDML apply errors (column not found, data type mismatch) begin appearing without any recent, obviously related DDL event being reported.
Possible CauseSource and target schemas have quietly drifted apart — a DDL change was made directly on the target, missed during an earlier gap, or applied out of order.
InvestigationCompare source and target DDL for the affected object directly (e.g. DESCRIBE/DBMS_METADATA comparison); check DDL history for any gap around the suspected drift point.
ResolutionReconcile the schema manually to match source intent, then verify no further DDL is pending; consider tightening DDL monitoring/alerting going forward.
ValidationSchema comparison shows source and target aligned, and DML apply errors on the affected object stop recurring.

Privilege Issues (DDL-specific)

SymptomDDL capture or apply fails specifically, while DML continues to work normally.
Possible CauseThe GoldenGate account lacks the additional privileges DDL support requires beyond standard DML capture/apply privileges (e.g. access to DDL trigger objects, metadata packages, or target DDL execution rights).
InvestigationCompare granted privileges against the documented DDL-support prerequisite list; check for DDL-trigger-specific objects that may be missing or disabled.
ResolutionGrant the missing DDL-specific privileges and re-enable/reinstall the DDL support objects if required.
ValidationA test DDL statement now captures and applies successfully end-to-end.
Treat DDL and DML as two independently-verifiable pipelines. A healthy DML lag number tells you nothing about whether DDL is keeping schemas in sync — validate both.

Initial Load Failure

SymptomThe bulk load method (direct load, file-based load, or database-native utility) errors out partway through, or completes with a row count that doesn't match the source.
CauseTarget constraints (PK/FK/unique) rejecting rows, insufficient target storage, network interruption mid-load, or a data type incompatibility only surfaced under real data volume.
CheckLoad utility logs for the specific rejected rows/errors; target tablespace/storage headroom; constraint definitions on the target relative to source data.
FixResolve the specific blocking condition (disable/adjust constraints for the load window, add storage, fix data type mapping), then restart or resume the load.
ValidationRow counts and, ideally, checksums/hashes match between source and target for the loaded tables.

CDC Start Position Issues

SymptomData captured after cutover to CDC is missing a window of changes, or the same changes appear to have been applied twice.
CauseThe SCN/LSN/timestamp used to start Extract did not precisely align with the exact point the initial load's data was captured from — typically too late (gap) or too early (overlap/duplicates).
CheckConfirm the exact SCN/position recorded at the moment of initial load extraction versus the SCN/position Extract was actually started from.
FixRestart CDC capture from the precisely correct position; if a gap or overlap already occurred, reconcile the affected window using the Data Mismatch process.
ValidationNo gap or duplicate window remains when comparing source transaction history to what was captured.

Missing Transactions

SymptomSpecific known source transactions never appear on the target, discovered via reconciliation or a downstream data-quality check.
CauseA filter unintentionally excluding relevant rows, a CDC start-position gap, or a transaction that failed apply and was routed to a discard/exceptions path without being noticed.
CheckDiscard file and exceptions handling configuration; filter/WHERE clauses on the relevant TABLE/MAP statements; CDC start-position accuracy.
FixCorrect the filter or start-position issue, then manually apply the specific missing transaction(s) after confirming they are genuinely absent.
ValidationTargeted row-level comparison confirms the previously-missing transaction is now present and correct on the target.

Duplicate Data

SymptomRow counts on target exceed source for the same logical dataset, or a unique-constraint violation appears during apply.
CauseOverlap between the initial load window and CDC start position, or a restart/reprocessing of trail data that had already been applied.
CheckCompare the initial load's data-as-of position against the CDC start position for overlap; check for any manual reprocessing of already-applied trail files.
FixIdentify and remove the duplicate rows using a reliable key, then correct the process (start position or replay procedure) that caused the overlap.
ValidationRow counts reconcile and the unique-constraint condition no longer recurs.

Replication During Migration — High Migration Lag

SymptomLag during the synchronization phase stays persistently high, delaying the point at which cutover can safely occur.
CauseThe same root causes as ordinary replication lag (see the Replication Lag and Performance tabs), often amplified by the initial-load backlog still being drained concurrently with live CDC.
CheckIsolate whether lag is concentrated on the capture side, the apply side, or a target-side bottleneck, exactly as in standard lag troubleshooting.
FixApply the relevant fix from Replication Lag / Performance Troubleshooting; consider a maintenance window with reduced source write volume if migration lag will not close otherwise.
ValidationLag trends down to, and stays within, the threshold defined as acceptable for cutover.

Cutover Issues

SymptomApplication errors or data inconsistency immediately after traffic is switched to the new (target) system.
CauseCutover executed before lag reached zero/near-zero, in-flight transactions at the exact cutover moment not fully drained, or a reverse-replication path not established for rollback safety.
CheckLag value at the exact cutover timestamp; whether a quiesce period was used to let in-flight transactions drain before redirecting traffic.
FixWhere possible, briefly quiesce writes, confirm zero lag, then cut over; if cutover already happened with a gap, reconcile the affected transaction window immediately.
ValidationPost-cutover validation (see below) confirms source and target fully agree as of the cutover point.

Post-Cutover Validation

SymptomN/A — this is a proactive step, not a symptom-driven one.
CauseN/A
CheckRow counts and, where feasible, checksums/hashes across critical tables; application-level smoke tests against the new system; any error logs generated in the minutes immediately following cutover.
FixAddress any discrepancy immediately using the Data Mismatch process before declaring the migration complete.
ValidationA formal sign-off comparing source and target as of the cutover point, retained as part of the migration record.

Source and Target Data Mismatch — Troubleshooting

Data mismatch is almost always discovered downstream of GoldenGate (by a reconciliation job or a business user), which means the investigation has to work backward through the pipeline to find where things diverged.

Missing Rows

Identify: Target row count is lower than source for a given table/window; a specific known key is absent on target.

Investigate: Check the discard file for rejected operations referencing that key; check filters/WHERE clauses that might exclude the row; check whether the source transaction was ever captured at all (Extract-side).

Isolate the transaction: Use the trail's transaction ID / CSN and, if available, GoldenGate logdump or trail scanning to confirm whether the operation ever reached the trail, and if so, whether it reached Replicat.

Validate: Confirm the row is genuinely absent (not a timing artifact of an in-flight comparison) by re-checking after lag reaches zero.

Resolve: Manually apply the specific missing transaction after root-causing why it didn't apply automatically, to prevent recurrence.

Extra Rows

Identify: Target row count exceeds source; a key exists on target with no corresponding source row.

Investigate: Check whether the row was inserted directly on the target outside of GoldenGate (a common cause), or whether a delete on the source failed to replicate.

Isolate: Compare the row's last-modified/audit metadata (if available) against GoldenGate's apply history to determine whether it originated from replication or from a direct target write.

Validate: Confirm the source truly has no matching row (not a filter exclusion that is working as intended).

Resolve: Remove the extra row if confirmed erroneous, and close off whatever direct-write path or replication gap allowed it.

Different Column Values

Identify: Row exists on both sides with the same key, but one or more column values differ.

Investigate: Check for column mapping/transformation logic (COLMAP, conversion functions) that may be behaving unexpectedly; check for an update on target applied out of order relative to source.

Isolate: Trace the specific update transaction for that row through the trail to see exactly what value GoldenGate applied and compare it to what the source actually held at that time.

Validate: Re-run the comparison after confirming zero lag, since an in-flight update can look like a mismatch if compared mid-flight.

Resolve: Correct the target value from the authoritative source value, and fix any transformation logic found to be at fault.

Duplicate Rows

Identify: The same logical row (by business key) appears more than once on the target where the source has only one.

Investigate: Check for a key-mapping or KEYCOLS misconfiguration causing GoldenGate to treat updates as inserts; check for trail reprocessing/replay overlap (see Initial Load & Migration).

Isolate: Compare the duplicate rows' apply timestamps/transaction IDs to determine whether they came from a single replay event or from a persistent key-handling defect.

Validate: Confirm the correct unique key definition on target matches the actual source business key.

Resolve: De-duplicate using the authoritative source row, and correct the KEYCOLS/key configuration if that was the root cause.

Missing Transactions

Identify: A specific business event (e.g. a known order or payment) is not reflected anywhere on the target, even though related rows otherwise look consistent.

Investigate: Check the discard file, DDLERROR/REPERROR handling rules, and exceptions routing for that time window.

Isolate: Use the source transaction's identifying attributes (timestamp, key, approximate SCN) to search the trail and confirm at which stage it disappeared.

Validate: Confirm against source audit data that the transaction did in fact commit on the source.

Resolve: Manually replay the specific transaction and fix the handling rule or filter that caused it to be dropped.

Out-of-Order Transactions

Identify: Final column values on target don't match the source's final state, even though the individual updates all appear to have arrived — symptomatic of updates applied in the wrong sequence.

Investigate: Check for parallel apply configurations (parallelism/grouping) that may have relaxed strict commit ordering on interdependent rows; check for multiple concurrent Replicat threads applying to the same row without adequate coordination.

Isolate: Reconstruct the actual apply order from Replicat's transaction history/log and compare it to the true source commit order for that row.

Validate: Confirm the row's current value equals the source's true final value once ordering is corrected.

Resolve: Correct the value from source, and reassess parallelism/grouping settings for rows with strict ordering dependencies.

Oracle GoldenGate Veridata is Oracle's dedicated data-comparison product and is the appropriate tool for systematic, repeatable, large-scale source/target comparison — rather than ad hoc row counting — especially for periodic reconciliation, post-migration validation, or ongoing data-quality assurance on high-value tables. It identifies out-of-sync rows without requiring replication to be paused, and is the recommended option wherever mismatch detection needs to be routine rather than one-off.

Scenarios

Worked, end-to-end troubleshooting walkthroughs that combine several of the topics above the way a real incident usually does.

Scenario 1 — Replicat lag climbing steadily over 3 hoursLag · Performance
Observed: Replicat lag rises from under a minute to over 40 minutes across a business day; Extract lag stays low the whole time.
Step 1: Since Extract lag is low, focus target-side: check target database CPU, I/O wait, and blocking sessions during the lag window.
Step 2: Target-side monitoring shows rising I/O wait correlated with a nightly index-rebuild job that overlaps business hours today due to a scheduling error.
Step 3: Confirm via INFO REPLICAT, DETAIL that apply throughput (ops/sec) drops in lockstep with the I/O wait spikes — consistent with a target database performance bottleneck, not a GoldenGate defect.
Resolution: Reschedule the index rebuild outside business hours; lag drains back to baseline once target I/O contention clears.
Scenario 2 — Extract abends with OGG-02650 after a schema renameErrors · DDL
Observed: Extract abends citing a source wildcard specification catalog-name mismatch shortly after a PDB/catalog-related schema reorganization.
Step 1: Search the Errors tab for OGG-02650; confirm the cause matches — a TABLE wildcard specification that doesn't include a catalog name while the resolved source table name does.
Step 2: Compare the TABLE statement in the parameter file against the actual fully-qualified table name Extract resolved from the catalog after the reorganization.
Resolution: Update the TABLE wildcard specification to include the catalog name consistently, matching the new schema structure, and restart Extract.
Validation: Extract starts cleanly and begins capturing the affected tables with no further OGG-02650 occurrences.
Scenario 3 — Reconciliation job reports 40 missing rows after a migration cutoverMigration · Mismatch
Observed: A post-cutover reconciliation job flags 40 rows present on source but absent on target, all with timestamps within a five-minute window around the cutover time.
Step 1: Check the CDC start position used when Extract began capturing versus the SCN recorded at the moment the initial load extracted its data — a classic CDC start-position gap.
Step 2: Confirm the gap: the CDC start SCN is found to be several seconds later than the initial load's true as-of SCN, exactly enough to explain the missing window.
Step 3: Isolate the 40 specific transactions from source audit data for that window.
Resolution: Manually apply the 40 missing transactions to target, then update the migration runbook to always capture the CDC start SCN from the same query used for the initial load's as-of point.
Scenario 4 — Distribution Service repeatedly disconnects from Receiver ServiceSecurity · Trail
Observed: Remote trail growth is intermittent; Distribution Service logs show repeated connection resets to the target-side Receiver Service every few minutes.
Step 1: Check for a TLS handshake failure or certificate issue in the Distribution/Receiver logs at the exact disconnect times.
Step 2: Logs show the target-side certificate expired two days prior — the connection succeeds briefly on retry due to a load balancer occasionally routing to a node with a still-valid cached session, then fails again.
Resolution: Renew and redeploy the certificate on the target-side Microservices deployment; confirm the trust store on the source side references the correct, current CA.
Validation: Distribution Service maintains a stable, uninterrupted connection and remote trail growth becomes continuous again.
Scenario 5 — Same value appears different on source and target for a subset of updatesData Mismatch
Observed: Veridata comparison flags column-value mismatches on roughly 2% of rows in a high-write table, all involving rows updated multiple times in quick succession.
Step 1: Check whether Parallel Replicat with high parallelism is applying updates to the same row from different worker threads without guaranteed ordering for that row's key.
Step 2: Reconstruct apply order from Replicat's transaction history for a sample of mismatched rows; confirm updates were applied out of source-commit order.
Resolution: Correct the mismatched rows from source, then review parallelism/grouping configuration for this table's hot-row update pattern, since default parallel apply assumed independence between rows that was not actually present.
Validation: Subsequent Veridata comparisons over the same table window show no new column-value mismatches.
