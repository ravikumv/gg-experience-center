Pre-Requisite Checklist
Ensure all prerequisites are met before enabling supplemental logging and ADD TRANDATA. Use the checklist below to track progress.
☑️ Setup Checklist
0 / 8 Complete
🔴 Database-Level Prerequisites
ARCHIVELOG Mode
  • ✔Oracle DB must be in ARCHIVELOG mode
  • ✔GoldenGate mines archived redo logs for changes
  • ✔Check: SELECT LOG_MODE FROM V$DATABASE;
  • ✔Enable: SHUTDOWN → MOUNT → ALTER DATABASE ARCHIVELOG
Minimal Supplemental Logging
  • ✔Must be enabled at DB level before TRANDATA
  • ✔Requires SYSDBA or ALTER DATABASE privilege
  • ✔No instance restart required
  • ✔Works in RAC — apply once per DB, not per node
FORCE LOGGING
  • ✔Prevents NOLOGGING operations from bypassing redo
  • ✔Critical for direct path loads, CREATE TABLE NOLOGGING
  • ✔Apply at DB level AND PDB level for multitenant
  • ✔Check: SELECT FORCE_LOGGING FROM V$DATABASE;
Redo Log Sizing
  • ✔Minimum: 3 redo log groups, ≥ 500MB each
  • ✔Supplemental logging increases redo volume by 5–40%
  • ✔Target: log switches no more than 4 per hour
  • ✔Monitor: V$LOG_HISTORY for switch frequency
🛠️ GoldenGate Software & Network Prerequisites
Software Requirements
  • ✔Oracle GoldenGate 26ai Microservices installed
  • ✔OGG_HOME and ORACLE_HOME environment variables set
  • ✔ServiceManager running (AdminClient port 9100)
  • ✔Oracle Wallet configured for credential alias
Source DB Validation
  • ✔Tables to replicate have PRIMARY KEY or UNIQUE index
  • ✔No unsupported data types (BFILE, XMLTYPE — limited)
  • ✔Source schema accessible by GGS user (SELECT privilege)
  • ✔V$DATABASE shows LOG_MODE = ARCHIVELOG

GoldenGate Sizing Guidelines
Based on Oracle internal sizing guidelines. Use these formulas to plan memory, storage, and network for your GoldenGate deployment.
🧮 Memory Requirement Calculator (Integrated Extract)
ℹ️
By default, one Extract requests the logmining server to run with MAX_SGA_SIZE of 1GB. For 3 Extracts in the same database instance, allocate at least 3 GB to the Streams pool. Best practice: keep 25% of Streams pool available.
Example: 3 Extracts → set STREAMS_POOL_SIZE = 3 GB × 1.25 = 3.75 GB
STREAMS_POOL_SIZE = (Number of Extracts × 1 GB) × 1.25
STREAMS_POOL_SIZE = 3.75 GB
SQL to Apply
ALTER SYSTEM SET STREAMS_POOL_SIZE = 3840M SCOPE=BOTH; -- Or in init.ora / spfile: STREAMS_POOL_SIZE=3840M
💾 Trail File Storage Calculator
ℹ️
Formula: ((transaction log size × 0.33) × log switches per day) × retention days
Example: 1GB logs, 10 switches/day, 7 days → 1 × 0.33 × 10 × 7 = 23 GB
Trail Storage = (Txn Log GB × 0.33) × Log Switches/Day × Retention Days
Trail Storage = 23.1 GB

⭐ Key Point

TRANDATA vs SCHEMATRANDATA
📊 ADD TRANDATA (Table)
  • Specific tables. DML capture.
  • Best for stable environments with controlled DDL.
🗄 ADD SCHEMATRANDATA (Schema)
  • All current and future tables.
  • Required for Oracle DDL replication. Recommended for production.
💡 Important Notes
  • Supplemental logging does not change your data. It only adds the information GoldenGate needs to identify and replicate changes accurately.
  • ALLCOLS logs all columns — required for bi-directional / CDR / Active-Active.
  • Minimal supplemental logging (database level) is the foundation.
  • TRANDATA not required for Initial Load. Required for ongoing CDC.

🎛️ ADD TRANDATA Options
Choose the right level for each scenario
🔑
Basic (Primary Key)
Logs PK columns only. Minimum required when a primary key exists. Best for standard OLTP tables.
ADD TRANDATA HR.EMPLOYEES
🗝️
NOKEY (Unique Index)
For tables without a primary key. Logs unique index columns or falls back to ROWID-based identification.
ADD TRANDATA HR.DEPT NOKEY
📋
ALLCOLS
Logs every column. Required for CDR (Conflict Detection & Resolution) in bi-directional replication.
ADD TRANDATA HR.EMPLOYEES ALLCOLS
🎯
KEYCOLS (Custom Key)
Define custom columns as the logical key. Overrides default key detection for legacy or composite scenarios.
ADD TRANDATA HR.EMP KEYCOLS (BADGE, SSN)

Schema-level supplemental logging. Auto-applies to new tables added later. Includes scheduling columns for Parallel Replicat.

PREPARECSN
Marks the SCN at which initial data load completed, enabling Extract to begin capture at the exact right point.

DML Statement

7
GoldenGate Trail

Extract processes the captured changes and writes them to the GoldenGate trail.

❓ GoldenGate Fundamentals — Frequently Asked Questions

  

  

    

      
        
        
        
      
      
        

          #
          Question
          Answer
        

      
      
        

          1
          What is Oracle GoldenGate?
          Oracle GoldenGate is a real-time data integration and replication technology that captures database changes and delivers them to target systems with minimal impact on the source.
        

        

          2
          How does GoldenGate capture database changes?
          GoldenGate captures database changes from transaction logs/redo. For Oracle Integrated Extract, the Oracle database logmining infrastructure mines redo and provides Logical Change Records (LCRs) to Extract.
        

        

          3
          Why is supplemental logging required?
          Supplemental logging adds additional information to redo that GoldenGate needs to reliably identify and capture database changes, particularly information needed for row identification.
        

        

          4
          What is TRANDATA?
          ADD TRANDATA configures table-level supplemental logging required for GoldenGate change capture, including appropriate key information for identifying rows.
        

        

          5
          What is SCHEMATRANDATA?
          ADD SCHEMATRANDATA configures schema-level supplemental logging for current and future tables. For Oracle, it is also required when replicating DDL with GoldenGate.
        

        

          6
          What is an LCR?
          LCR (Logical Change Record) represents a logical database change. With Oracle Integrated Extract, the database logmining infrastructure mines redo and provides LCRs to Extract for processing.
        

        

          7
          What happens when an INSERT, UPDATE or DELETE occurs?
          The database processes the DML, generates redo, and supplemental logging provides additional information according to the configured logging. Extract captures the change, writes it to the Trail, and Replicat applies it to the target.
        

        

          8
          Does GoldenGate always capture before and after images?
          No. Before-image information is not automatically captured for every change. The information available depends on database supplemental logging and GoldenGate configuration. Therefore, supplemental logging should not simply be described as PK + before image.
        

        

          9
          What are the main components of GoldenGate?
          The fundamental replication flow is Extract → Trail → Replicat. Extract captures changes, Trail stores captured changes, and Replicat reads the Trail and applies the changes to the target.
        

        

          10
          What is a GoldenGate Trail?
          A Trail is a sequence of files containing GoldenGate change records. It provides persistence between capture and delivery and decouples Extract from Replicat.
        

        

          11
          Why does GoldenGate use Trail files?
          Trail files decouple capture from delivery and provide persistent storage for captured changes. If the target or Replicat is temporarily unavailable, Extract can continue capturing changes while they accumulate in the Trail.
        

        

          12
          What is Initial Load Extract?
          Initial Load Extract is used to extract existing table data for an initial load into the target. It is different from transaction-log-based change capture.
        

        

          13
          What happened to Classic Extract?
          Classic Extract is a legacy/traditional GoldenGate capture architecture. For Oracle Database in GoldenGate 26ai, Classic Extract is no longer supported and Integrated Extract is used for Oracle transaction capture. Other databases such as MySQL, PostgreSQL, SQL Server and Db2 use their respective supported capture mechanisms.
        

        

          14
          What is Integrated Extract?
          Integrated Extract is the Oracle capture architecture that integrates with the Oracle database logmining infrastructure to mine redo and provide LCRs to Extract.
        

        

          15
          What are the main Replicat types?
          GoldenGate provides several Replicat architectures, including Parallel Non-Integrated Replicat, Parallel Integrated Replicat, Coordinated Replicat, Integrated Replicat, and Classic Replicat, with availability and support depending on the GoldenGate version and target database.
        

        

          16
          What is Parallel Non-Integrated Replicat?
          Parallel Non-Integrated Replicat uses GoldenGate-controlled parallel apply processes to improve throughput without using the Oracle database integrated apply server. It is the recommended default parallel apply option for many Oracle deployments in current GoldenGate releases.
        

        

          17
          What is Parallel Integrated Replicat?
          Parallel Integrated Replicat uses parallel processing together with the Oracle database integrated apply infrastructure. It is a distinct architecture from Parallel Non-Integrated Replicat and should be selected based on the target database, GoldenGate version and required features.
        

        

          18
          What is Integrated Replicat?
          Integrated Replicat uses the Oracle database integrated apply infrastructure to apply GoldenGate changes. In GoldenGate 26ai, Integrated Replicat is deprecated, and Oracle recommends Parallel Replicat for appropriate workloads.
        

        

          19
          What is Coordinated Replicat?
          Coordinated Replicat uses multiple apply threads coordinated by a Replicat process to improve apply performance while maintaining transaction dependencies.
        

        

          20
          What is Classic Replicat?
          Classic Replicat is the traditional single-process apply architecture. It is a legacy option and should not be presented as the preferred architecture for modern high-throughput Oracle deployments.

💻 Local RAG Setup — Python (LangChain + FAISS + Llama / Oracle 26ai)

        Python 3.10+
      

      

        

          

            
Step 1 — Install & Ingest

            

# Install dependencies
pip install langchain faiss-cpu
pip install sentence-transformers ollama
pip install pypdf unstructured

# Ingest GoldenGate docs
from langchain.document_loaders import PyPDFLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain.embeddings import HuggingFaceEmbeddings
from langchain.vectorstores import FAISS

loader = PyPDFLoader("goldengate_21c_admin.pdf")
docs   = loader.load()
splitter = RecursiveCharacterTextSplitter(chunk_size=512, chunk_overlap=64)
chunks = splitter.split_documents(docs)
embedder = HuggingFaceEmbeddings(model_name="sentence-transformers/all-MiniLM-L6-v2")
vectorstore = FAISS.from_documents(chunks, embedder)
vectorstore.save_local("gg_rag_index")
print(f"Indexed {len(chunks)} chunks")
            

          

          

            
Step 2 — Query with Local LLM or Oracle 26ai

            

from langchain.llms import Ollama
from langchain.chains import RetrievalQA

vectorstore = FAISS.load_local("gg_rag_index", embedder,
    allow_dangerous_deserialization=True)

# Option A: Local (Ollama / Llama3)
llm = Ollama(model="llama3.2")

# Option B: Oracle 26ai (via Anthropic SDK)
# llm = Claude(model="claude-sonnet-4-6")

qa_chain = RetrievalQA.from_chain_type(
    llm=llm,
    retriever=vectorstore.as_retriever(search_kwargs={"k": 5}),
    return_source_documents=True
)
result = qa_chain.invoke(
    "What supplemental logging level is needed for Lakehouse?"
)
print(result["result"])
