Oracle GoldenGate Veridata — Overview

Based on the official Oracle GoldenGate Veridata documentation (Release 26): what it is, the objects you configure to use it, how its components fit together, and the two-step process it uses to confirm data is actually out of sync.

A comparison and repair solution, not a replication engine

Oracle GoldenGate Veridata is a high-speed data comparison and repair tool that finds, reports on, and fixes data discrepancies across heterogeneous databases — without interrupting the business processes running against those databases. It's built to surface out-of-sync data before it causes a problem downstream, rather than after.

Why it matters alongside GoldenGate replication

Because Veridata standardizes and validates data across different database types, teams rely on it for confidence in mission-critical systems, data migrations, and disaster-recovery configurations — anywhere GoldenGate is keeping databases in sync and someone needs independent proof that the sync actually held.

The objects you build, in order

Setting up a comparison in Veridata means creating a small chain of objects, each one scoped by the object before it.

1

Connections

A Connection points the Veridata Server at a source or target database. The Server uses it to talk to the Veridata Agent running against that database.

2

Groups

A Group is a logical container for one or more Compare Pairs, tied to a set of source and target Connections.

3

Compare Pairs

A Compare Pair is the logical relationship between one source table and one target table for comparison purposes. Every Compare Pair belongs to a Group.

4

Jobs and Repairs

Compare Pairs only run inside a Job — the Job decides which Groups get processed. From the UI you can also repair a job's out-of-sync results, and for a handful of supported databases, generate a repair SQL file instead.

5

Users, User Groups & Roles

User Management lets you create and organize users and user groups, each assigned one or more roles.

AdministratorSuper UserMonitoring Operator Detail Monitoring OperatorRepair OperatorJob Operator Command Line Operator
6

Delta Comparison

Instead of re-comparing every row on every run, a Delta Processing Job compares only what has changed in the source and target tables since the previous job run.

7

Profile

A Profile is a named set of processing parameters that controls how a comparison or repair job behaves. Veridata ships a default Profile, but you can create your own and assign — or override — them per Job or per Compare Pair, including at run time.

⚙

Veridata Agent

A lightweight Java program that runs on the database system itself or remotely. It talks directly to the source or target database to fetch and return blocks of data rows and column-level detail, and to run the queries a repair needs.

📊

Veridata Server

Compares the data the Agents return, confirms which rows are genuinely out of sync, performs repairs, produces reports, and coordinates jobs across every other component.

🗃

Repository Database

Stores Veridata's own metadata — Connections, Groups, Compare Pairs, Jobs, Profiles, users. Veridata supports MySQL Server only for this repository, independent of whichever databases are being compared.

⌨

Vericom, Export & Import Utilities

Vericom is Veridata's command-line interface — every administration task available in the GUI can also be done here. The Export/Import Utilities move configuration between environments or versions (test to production, Veridata Classic to Next Gen); the Import Utility can also build Compare Pairs, Groups, and Jobs straight from a GoldenGate Replicat parameter file — the basis for the mapping shown in the next tab.

A two-step process, because replication has latency

Comparing live, continuously-replicated data risks false positives — a row can look out of sync simply because a change hasn't replicated yet. Veridata handles this with two stages: MOOS (Maybe Out of Sync) and COOS (Confirm Out of Sync).

STEP 1 · ROW HASH

MOOS — Maybe Out of Sync

  • Agent retrieves rows from source and target using a defined query
  • Data types are standardized across the heterogeneous source/target pair
  • Primary key values are fetched as-is; non-key column values are hashed to cut network transfer
  • Hashes are sent to the Server and compared
  • Any rows that look different are held in an in-memory MOOS queue — not yet reported
Why hold them back? With replication running concurrently, a "different" row may just be mid-flight — about to be corrected by the next replicated change.
STEP 2 · VALUE COMPARE

COOS — Confirm Out of Sync

  • Runs in parallel with Step 1, but each row waits out a configurable replication-latency delay first
  • After the delay, Veridata re-queries actual (unhashed) values for every column, source and target
  • Confirm-out-of-sync lookups can be batched and run in parallel — good for remote databases
  • Every MOOS row is resolved to one of three outcomes
In Flight — was out, replication just fixed it
In Sync — confirmed matching
Persistently Out of Sync — confirmed, reported

Two profile settings that control this behavior

Delay Confirm-Out-Of-Sync By (seconds) — how long a MOOS row waits before COOS re-checks it. Set this close to your normal replication lag to avoid false out-of-sync results.

Perform Confirm-Out-of-Sync Step — lets you skip COOS entirely and report straight off the row-hash step, useful when source activity is quiesced or the target isn't being continuously updated.

Connections — how the Veridata Server reaches each database

A Connection isn't a direct database login. It points the Veridata Server at the Veridata Agent running near a database — by host and port — and the Agent's own datasource is what actually talks to that database. Connections are created and managed on the Connections page, and only users with the Administrator or Super User role can create, edit, or delete them.

What defines a Connection

Host Name

DNS name or IP of the machine running the Veridata Agent — not necessarily the database host itself.

Port

The Agent's port — server.port in agent.properties for a Java agent, or INFO MANAGER in GGSCI for a C-agent.

Database

Auto-detected when you click Verify. Shows as Not Specified if the agent wasn't started with database details.

Credentials

A datasource user/password, plus an optional separate repair user with update and query privileges for target fixes.

GoldenGate parameter file to Compare Pairs

The Veridata Import Utility (run through vdt-import.sh / vdt-import.bat, part of Vericom) can build Connections, Groups, and Compare Pairs two ways: from a Veridata configuration.xml file, or by pointing it directly at a GoldenGate Replicat parameter file. Either way, the same TABLE/MAP/KEYCOLS mapping that drives replication is what ends up defining the compare pair.

The key-column mapping is what Veridata joins rows on — the same key columns GoldenGate uses to route change records.

4 · Steps to Import in the GUI

Prefer a point-and-click path over Vericom? The same GoldenGate parameter file can be loaded from the Web Console.

1

Log in to the Veridata Web UI

Open the Veridata Web UI and log in with a user that has configuration privileges (Administrator or Super User).

2

Open Utilities

Click Utilities in the main navigation menu.

3

Switch to the Import tab

Select the Import option/tab — the Export tab is shown by default.

4

Choose the GoldenGate parameter file option

Select the option to import from a GoldenGate parameter file (.prm) rather than a Veridata configuration.xml.

5

Browse and select the file

Click Browse File and select your target or extract .prm file from your local system.

6

Click Import

Click Import to parse the file and load the resulting Connections, Groups, and Compare Pairs into your repository.

Oracle GoldenGate Veridata Supported Use Cases

In a hybrid, multi-location IT environment — the same data often living in more than one system, or moving between them — some drift is almost inevitable. Left unchecked, bad data leads to poor decisions, missed SLAs, and operational, financial, or legal risk. The following are the use cases Oracle GoldenGate Veridata is built to support.

🔁

Data Migration

Moving data from one location or system to another — and confirming afterward that nothing was lost or altered in transit. Data validation immediately after migration is the critical last step: the new system has to function correctly and hold the same data integrity as the old one.

Database upgrades Cloud migration Data center relocation Post-migration validation
📄

Auditing & Compliance

As compliance expectations rise, organizations and their leadership are held to increasingly strict standards of accountability — including proving data accuracy to regulators. Veridata's comparison reports support that evidence trail.

HIPAA PCI-DSS GDPR
⚖

Data Consistency

In any replication scenario — data center to data center, on-premises to cloud, or relational database to data lake — it's essential that no discrepancies creep in between source and target. Veridata is the independent check that consistency actually holds.

⬆

Application Upgrades

Application upgrades typically fire a large volume of DDL and DML against the database. Where replication is already configured, it's essential to confirm every one of those source-side changes landed accurately on the target — exactly what a Veridata compare pair verifies.

These four use cases map directly onto this simulator's setup: the Oracle → 26ai / DB2 → 26ai / SQL Server → 26ai compare pairs model both a migration validation check and an ongoing data-consistency check against GoldenGate replication.
